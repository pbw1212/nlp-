## 测试范围

本轮使用真实配置的 Groq OpenAI-compatible Provider 和临时数据目录，未触碰本地真实
`.agent_data/`。覆盖了：

- 基础问候、静态知识、复杂规划和计算器调用；
- 无天气/股价工具时的动态事实请求；
- `/remember` 显式记忆、记忆查询、跨会话召回；
- 三轮任务约束、多轮修改、任务总结、旧会话恢复；
- `/help`、`/provider`、`/calc`、`/time`、会话/任务/记忆命令、空参数、未知命令和退出；
- 14 个确定性 Product Trial 场景、50 步确定性 fuzz、297 个自动化测试。

## 已验证可用

1. 基础自然语言回答成功。
2. 对没有真实工具支持的天气和股价请求会明确拒答，没有编造实时数据。
3. 计算器自然语言调用结果正确；`/calc` 和 `/time` 是本地直达路径，不需要模型往返。
4. 显式记忆可以写入 SQLite，并能在同一会话、新会话和恢复旧会话后召回。
5. `/provider` 只显示 Provider、模型、端点、变量名和配置状态，不显示凭据值。
6. 无效的会话、任务、记忆 ID，以及空参数和未知命令不会使进程退出。

## 发现的问题

### P0：无效 `/memory-history` 会导致 CLI 崩溃（已修复）

复现：`/memory-history bad_id`。旧行为会抛出 `MemoryNotFoundError` traceback 并退出；
现在返回“未找到记忆历史或 ID”，交互循环继续。回归测试位于
`code/tests/test_personal_agent_app.py`。

### P1：Task 3 的真实模型提案不够可靠（部分修复，历史测试结论）

黑盒数据中出现了两类证据：

- 普通计算请求被写成 `PROGRESS` 条目；普通记忆查询被写成 `OPEN_QUESTION` 条目；
- 用户要求修改第二天行程时，回答声称“已更新”，但 Task 3 事件实际为 `REJECTED`，
  原因是模型提交了无效 `SUPERSEDE` 目标。

当前系统会保留拒绝事实并在回答后显示 warning，没有伪造已落盘状态。之后已删除按问句、假设词和完成词猜测语义的硬编码过滤；现在由模型提出语义 proposal，运行时只执行来源权限、证据、目标存在性和生命周期不变量校验。任务修改失败时仍必须让最终回答明确说“未写入任务状态”。

### P1：真实自然语言回合延迟偏高（未修复）

本轮单回合约 13–79 秒；复杂回合通常要经过 Task 3、记忆检索/解释和 Main Agent 多次
Provider 请求。CLI 有等待提示，但长时间等待仍是明显体验问题。应先做请求级耗时统计和
阶段预算，再在不牺牲真实性的前提下减少空记忆解释、无变化 Task 3 更新和重复推理。

### P1：动态事实工具能力仍缺失（已如实拒答）

本报告测试时没有天气、新闻、股票等真实外部工具。拒绝编造是正确行为，但产品尚不能称为通用
个人 Agent；接入工具时必须同时加入来源、时间戳、失败和权限边界，不能只改 Prompt。

### P1：长会话压缩（本报告时点未实现，当前已补齐）

本报告记录的是旧实现：当时是有界窗口截取，不是可审计的摘要压缩。当前已改为模型感知窗口、持久化 compaction checkpoint 和完整 Transcript 保留，见 `docs/architecture/task3-working-state.md`。

### P2：自动长期记忆曾默认关闭（当前已改为批量后台默认开启）

旧版本最低可用记忆依赖显式 `/remember`。当前普通成功轮次默认进入可重试的批量缓冲区，由 NEMORI 结合多轮上下文沉淀；不再执行单轮正则晋升。自动提炼仍需通过真实 Provider 做误写、冲突、撤回和用户可见审计。

## 后续演进顺序

1. 继续用真实 Provider 验证 Task 3 proposal 与失败语义的用户可见一致性。
2. 建立每轮阶段耗时/Provider 次数的无敏感遥测，降低空操作和重复请求。
3. 补齐外部事实工具的真实调用、来源展示、超时、权限和失败模型。
4. 用更长的真实多轮实验验证可追踪 compaction 的约束保留、失败恢复和重启恢复。
5. 最后再评估自动记忆提升和人格/认知建模；所有自动写入必须可解释、可撤回、可审计。
